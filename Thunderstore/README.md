# CombatPanel

独立 GTFO 战斗统计面板：局内查看战斗数据，成功或失败结算查看队伍贡献。仅依赖 **BepInEx-BepInExPack_GTFO-3.2.4**；EWC（ExtraWeaponCustomization）是可选集成，不是依赖。

**源码 / Source：[GitHub — hawchou1995/GTFOCombatPanel](https://github.com/hawchou1995/GTFOCombatPanel)**

## 安装

- **模组包管理器（Thunderstore Mod Manager 等）**：搜索 `CombatPanel` 安装到 GTFO profile，BepInEx 依赖会自动带上。需要共享统计的每台机器装同一版本。
- **手动安装**：先把 BepInEx 装进 GTFO 目录，再把包内 `BepInEx/plugins/GTFOCombatPanel/` 整个目录原样放进同一路径。
- `CombatPanel-config/scoring.json` 放在游戏持久数据目录（GTFO 即 `…\AppData\LocalLow\10 Chambers Collective\GTFO\`）下，只在缺失时写入一次；插件目录里的旧副本首次使用时会自动导入、此后以持久目录为准——你手改过的配置不会被覆盖，也不会被安装/更新包换掉，写错的内容整份判为无效并保留上次有效值。
- `F8` 在关卡内显示 / 隐藏 HUD 表。结算页上按一次收起板子（恢复原版页面），再按一次交回自动判定；它的「出板」用的是兜底条带，**不绕过页面的测量门**：客机失败页量不到「同一个原生返回位置」的几何时（既没有主机页量的那个「返回大厅」按钮的已布局矩形，也没有等待提示真正渲染出来的字形），板保留原版页面、过一会儿再重测，`F8` 不会让它提前出来，也不会给出一条跨过那行提示的带；板旁那个锚在同一行提示上的鼠标开关也等提示真的画出来才出现。
- 多人：快照协议为 **v8**，与旧协议明确不兼容（旧协议包会被拒收，不是"勉强可用"）。

## 局内 HUD

`F8` 显示 / 隐藏。默认列：

`玩家 | 伤害 占比 | 友伤 | 命中率 | 弱点率 | 总弹丸 命中 弱点`

伤害只含敌伤；占比按已观测队伍敌伤计算。`~` 表示估算或分母只覆盖已获得的数据；无观测显示 `—`。不按伤害反推命中或弱点。武器行占比使用该武器敌伤；玩家总伤可包含工具，因此两把枪占比之和不一定等于玩家总占比。

## 局外结算

成功 / 失败均显示固定布局的影响力矩阵，按综合评分降序排列。保留原表格行与布局，**工具动作和工具统计只在结算显示**。

十三项指标：总伤害、硬直、击杀、救援、弱点率、命中率、补给效率、工具效率、独存、倒地、友伤、近战击杀、触手击杀。击杀可分小怪 / 精英 / BOSS，基础价值分别 **0.5 / 1 / 1.5**。分档称号只分解同一击杀评分，不重复加分。友伤**伤害**不超过容差（`scoring.json` 的 `FriendlyFireGrace`，默认 10，范围 0–1000）时按 0 计入评分；友伤**致倒**次数不受容差影响，照常计入，仍可能因此被评「敌我不分」；超过容差的伤害照旧按全队最大友伤归一惩罚。

- 炮台：发射、有效命中和工具敌伤。
- 绊雷：工具部署、回收、触发及工具敌伤。消耗品野雷只归部署者总伤，不加入工具部署 / 触发或当前工具行。
- 胶枪：真实弹丸发射、命中和胶住敌人等已有统计。
- 扫描：使用与确认标记；候选可标记列表不是成功扫描。机器人窗口计次仍保留估算标记。
- 近战只认近战伤害，Push 不算；触手击杀按游戏原生的 `IsScout` 身份判定。
- 沉睡是致死前明确观察的状态；无法判定保留未知，未知无额外加成，不冒充清醒或沉睡。
- 补给行（`补给效率 / 弹药包 / 工具包 / 血包`）的三个分项都归实际受益者，不是拿包操作的人；全满且没有实际收益不计。三类只有在真的观测到分裂时才打印，未分裂时第 3、4 格显示 `?`（不是 0）。补给效率本身仍按每次事件的「实际有效量 ÷ 应有量」取平均，给别人补给照旧计入。
- 失血只累计伤害回调中的实际生命损失，治疗不抵扣；上限变化本身不算失血。

## 结算板的落位与字号

两个结算页的板子都**优先从页面自己量得到的上下边界落位**，量不到时改用兜底条带，**不会空屏**（唯一例外是量不到下沿的客机失败页：那一档保留原版页面，见下）：

- 严格条带的前提是页面自己的动画已经结束：失败页要求原生 `任务失败` 标题**文字已经完整显示**（它的透明度乘以上层所有 CanvasGroup，达到满不透明）**并且**实测底边连续两次读数一致；成功页要求「已清理分区」图标行与完成区块的实测边稳定。文字还在淡入、只有矩形不动，不算就绪——那正是「标题字样还没渲染完就出评分面板」这一现象的来源。
- 上下边界是写死的一条带：**上边界**取「已清理分区」图标行（含该行标签）的实测底边加净空（1080p 16 px，按窗口高度等比缩放）；**下边界**取本机真正能看到的页脚——主机是「返回大厅 / 送所有囚犯回大厅」按钮上沿；客机量的是**同一个原生返回位置**：主机页那个「返回大厅」按钮在本页的已布局矩形，与「正在等待…」那行字真正画出来的字形，两者取更靠上的那个（客机上按钮不可点，但它在页面上；布局框、别的可按控件都不算）——再减同一净空。板子自上边界向下顶对齐铺开，**不是居中**，所以带越高表越大、字号越大。
- **真实锚点拿不到时的兜底**：主机页、成功页与固定模式在量不到锚点时用「屏幕安全区」兜底出板，绝不空屏——兜底同样只用上面那两条边，两边都量不到时才退到窗口安全区，并且仍然避开扫描到的任何原生控件；兜底板逐帧重测，遇到遮挡是**位移或降低不透明度**，不是消失。**客机失败页是例外**：上面那个原生返回位置与提示字形都量不到时，它保留原版页面、按既有节流重新测量，不拿布局框、别的控件或屏幕底边凑一条边界，**`F8` 也不会**；一条必须跨过那堵墙才能装下板的兜底带同样拒收。一旦页面的真实锚点稳定可测，板子自动回到严格条带，不需要 `F8` 关开。
- 带太高或太矮都不会压到上方：带高决定行高与字号（带不够时缩字号、收行距）；板子比带还高时保持上边界不动、**越过下沿时按 0.55 变淡绘制，绝不压上方图标行**。
- 字号由这段条带按固定行数搜索得到（最高为局内字号的 3.5 倍）；带太矮时按带高给出更小的字号，可读下限只是偏好——带不够时宁可缩小字号，也不把板子画到边界之外。**表格能填到条带的哪一处分两种情形：量到了下沿的页面（客机结算页那个原生返回位置或提示字形，带子本身已经停在那条边上方一段净空）可以填到自己的下沿，也就是 100%；主机页那条由「返回大厅 / 送所有囚犯回大厅」按钮界定的带，以及量不到下沿时改为保留原版的客机失败页，仍按原舒适上限停，表格最多用到条带高的 96%——按钮和页面边缘都不会被压到。**两种情形都在页面可用宽度用尽时停。板子落位后不会因为一两帧的抖动移动；**页面本身在落位后又明显移动或改变尺寸时（别的模组重排页脚、分辨率变化等），板子会自动重新测量并按新条带重新拟合**。
- 结算页仍在持续收快照：数据让表格变大时，会先按落位时真正用到的条带与该帧按钮净空校验，装不下就保留已上板的网格，绝不压按钮或标题。

鼠标滚轮在板子上**滚动表格**（`F8` 强制出板时同样有效）：一格 = 一行，玩家姓名所在的表头行与右上角关闭按钮固定，滚到最后一行为止，表外不画。字号不再由滚轮改——它是页面量出的可读字号乘玩家在文件里写的手动倍率（`[Results] SuccessFontScale` / `FailureFontScale`，见下），并且永远不低于可读下限：装不下的行改成滚动，不会先缩成看不清的小字。

### 固定模式：自己定死字号和位置

不想让板子跟着页面的量测走，就在 BepInEx 的 `.cfg` 里打开 `[Results] FixedLayout = true`，再用三个键定死（成功页与失败页共用这组值）：

- `FixedFontPixels`（默认 `18`）：字号，单位是**实际屏幕像素**——画出来就是这个值，不乘任何系数，小数四舍五入到整数像素。有效范围 `1`–`240`，写 `5` 就是 5px，不会被抬到某个「可读下限」。
- `FixedAnchorX` / `FixedAnchorY`（默认 `0.5` / `0.8`）：表格**底边中点**的位置，两个值都是窗口尺寸的比例；**左上角是 `(0,0)`，X 向右增大、Y 向下增大**。算式为 `左边缘 = X × 窗口宽度 − 表格宽度 ÷ 2`、`上边缘 = Y × 窗口高度 − 表格高度`：表格从底边中点向上生长，人数或内容宽度变化时保持这个比例锚点。有效范围 `0`–`1`。

打开后，页面条带、下界墙、手动倍率（`SuccessFontScale` / `FailureFontScale`）与 `[Results] OffsetX/OffsetY` 都不再参与；滚轮仍然只滚动，从不改字号与锚点；关着时这四个键一个字节都不读。给的数字不会被悄悄改成别的值——字号不在 `1`–`240`、锚点不在 `0`–`1`、窗口尺寸不可信、该字号量不出表格、量回来的不是你要的那个像素、矩形跑出屏幕，这些都**不画板、不改你的数字、也不隐藏原版块**，只写一行 `fixed-layout-*` 诊断说明原因。锚点是中点 / 边，所以 `FixedAnchorX = 1` 会让表格有一半在屏幕外并被拒绝，把 X 调回接近 `0.5` 即可。

固定模式**不等**页面自己的下界墙，位置完全由你给的数决定；但它每一帧都做**真实二维矩形相交**检查（X 与 Y 都算，按钮上沿留 6px 净空）：压在一个真正可按的控件上时**照样画板**，只降到 `0.55` 不透明度减少遮挡，并在日志里写清固定矩形、真实字号、锚点、与哪个控件相交以及 opacity；X 错开就不算冲突，重叠消失立刻回到 `1.0`。扫描证据不足时（交互扫描不完整、或有 active 控件当帧量不到矩形）同样淡画，并且**原版块不隐藏**——只有这块 overlay 真的替代原版块（扫描完整、无重叠）时才让位。板下面那颗按钮仍然归它自己：overlay 不接管鼠标点击，只有滚轮被它吃掉用来滚动（字号只由 `FixedFontPixels` 决定，滚轮一个字节都不写配置）。`F8` 强制出板与改配置热重载在固定模式下同样生效，保存后下一帧就按新值重排。

## JSON 配置

评分配置位于游戏持久数据目录下的 `CombatPanel-config/scoring.json`（GTFO 即 `…\AppData\LocalLow\10 Chambers Collective\GTFO\CombatPanel-config\scoring.json`）。修改已有文件对应字段；插件不覆盖已有手改配置（旧插件目录里的那份只在首次使用时导入一次），无效内容保留上次有效值。缺失字段使用默认值。

```json
{
  "SleepingKillMultiplier": 2.0,
  "Titles": {
    "Damage": { "Title": "火力核心", "Description": "总伤害突出领先" },
    "MinorKills": { "Title": "杂兵清道夫", "Description": "小怪击杀贡献领先" },
    "EliteKills": { "Title": "精英猎手", "Description": "精英击杀贡献领先" },
    "BossKills": { "Title": "首领终结者", "Description": "BOSS 击杀贡献领先" },
    "TeamPillar": { "Title": "平平无奇", "Description": "没有突出领先的有效项目" }
  }
}
```

称号最多 16 字符，描述最多 96 字符；保留默认文字时随语言设置切换。`ZeroScore` 为旧配置保留项，本版不会绕过 top 规则强制授予零分称号。手动字号倍率写在 BepInEx 自己的 `.cfg`（`[Results] SuccessFontScale` / `FailureFontScale`，默认 1.0，范围 0.5–2.0）；滚轮只滚动，不改这两个键。

分配顺序：总评分降序；同分按稳定玩家身份顺序。只取启用、权重非零、有有效数据且独占 top 的项目。并列 / 全零不产生领先；倒地和友伤要求真实负面最严重。按正向 / 负向实际贡献绝对值选最大候选；重复称号由排序靠前者先得，其余尝试下一候选。无候选时按名次收尾：`#1`（含并列第一）拿「全能中坚」，其余拿中性称号「平平无奇」；这两句都不占位、可以重复。有单项独占的第一名仍拿那一项（例如「清道夫」），不会被改判「全能中坚」；全队显示分都是 `0.0` 时没有「第一」可站，一律中性。

默认权重：`TotalDamage .95, Stagger 1.40, Kills .70, Revives .28, WeakspotRate .44, Accuracy .28, SupplyEfficiency .78, ToolEfficiency .80, LoneSurvivor 1.60, Downs .55, FriendlyFire .75, MeleeKills .55, ScoutKills .60`。评分限制在 0–100；无数据、失败独存、禁用项目不制造有效贡献。工具效率的评分来源仍为扫描首次标记，其他工具统计只是显示，不暗中增加权重。

## 多人和兼容

每台机器独立评分，不将本地权重强加给队友。快照传输观测数据，主机负责其可测的伤害，玩家本人提供其本机命中、补给和扫描。没有数据来源的字段仍可能为空；主机没装模组时，装模组客机之间只共享可观测子集，`~` 不表示完整全队实测。称号与综合评分同样由本机判定：两端 `scoring.json` 不同时，同一局里各端可能看到不同的称号。

EWC 是可选集成，**不是强依赖**。公共 DLL 始终带无程序集强引用的运行时弹丸桥接；无 EWC 也可加载。接口契约按已检查的 EWC 版本验证，不保证任意第三方改版行为。普通射线与延迟弹丸分别去重，真实命中部位用于弱点判断。

结算会把每张成功/失败页写成一份 JSON 记录（**主档**），存在游戏持久数据目录下的 `CombatPanel-results\`（Unity `Application.persistentDataPath`；GTFO 即 `…\AppData\LocalLow\10 Chambers Collective\GTFO\CombatPanel-results\`，路径由游戏给，不在本模组里写死），文件名带毫秒时间、局次、Rundown/关卡与成败；旧插件目录里的历史记录首次使用时一次性导入。**同时**会在**本模组 DLL 旁的 `Results\`** 写一份**同样内容**的副本，方便直接找到或发给别人：两份字节一致、随同一块屏的数据一起刷新；写副本失败只影响副本，主档照常（日志写明原因与主档路径）；已有同名文件不会被覆盖（重名自动加数字后缀），玩家删掉副本后不会自动重建；`Results\` 不参与历史导入，也不会被扫描或回填。**本模组从不自动删除这些记录**——只有玩家自己删除才会消失；升级、重装都不会动它们。Rundown 和关卡在文件里分开记录。更多实现和构建说明见 [源码仓库](https://github.com/hawchou1995/GTFOCombatPanel)。

## 验证边界

本模组的结论分两类，不混用：**编译与托管重放断言**（`scripts/Verify.ps1` 对真实 BepInEx / Interop 程序集构建并跑无 Unity 的策略与场景重放，可复现）；**实机观察**（截图、日志、手感，只在明确记录时才算证据）。断言覆盖不到 Unity 原生回调时序、页面动画的实际轨迹和玩家屏幕前的观感，这类结论一律需要实机复核才能成立。逐版的验证记录与未验证项写在包内 `CHANGELOG.md`。
