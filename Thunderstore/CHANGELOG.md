# Changelog

## 1.19.20
- **根因（结算板被判「太小」实际上是被判「不许画」）**：`_boardFloor` 过去是**常量** 270px——30 行 × 6px 最小可读字形 × 1.5em 行高——并被当成「这页能不能放板」的判据。实机日志（1920×1440，主机成功页）里同一条带子在两帧之间测得 269px 与 286px，得到的却是相反答案：`success board deferred: need=270px ... have=240px`（整块不画）对 `glyph 6px filling 93%`（画了）。269 与 286 只差 17px，跨过的却是一个**可读性偏好**，不是房间的真实容量——这张表在 `HudTable.BuildGrid` 的下限处只需 30 × 3px × 1.5 = **135px** 就能画出来。
- **A：判定用的下限改成「这间房里最小能画多高」（新增纯托管 `ResultsFontGrowth.DrawableBoardHeight`）**。`MinimumBoardHeight`（可读下限 270px）**原样保留**，它回答的是「表想要多高」，仍是拟合目标；页面的**判定**改用 `DrawableBoardHeight(rows, rowEm, density, room)`：带子容得下可读下限就返回 270px（行为不变），容不下则返回最短可画网格，带子未测量（NaN/0/负）时仍返回可读下限。于是 269px 的带子得到 135px 的门槛并可画，而不是被判死。
- **D：消除悬崖，并让 `need=` 这个名字不再说谎**。`SuccessRegion` 现在先用本帧实测带子（及其本帧行数）算出 `stripFloor` 再问角色策略，并把结果回写 `_boardFloor`，使拟合、fail-open 阶梯与所有日志行引用**同一个数字**。`success board deferred` 行的语义从「需要 270px（可读）」改为「按最短可画网格需要 N px（可读下限 M px）」，一页一行的拒绝理由从此是关于房间的，而不是关于偏好的。
- **B：击杀分级行数与「买到的字号」挂钩（`ImpactBoard.SplitKillTiersFor`）**。`ImpactBoard.Build(report, true, ...)` 的常量 `true` 改为按本帧带子决定：`glyph = floor(room / rows / emPerGlyph)`，只有当**折叠两行（30→28 行）真的能把字形撑大一整像素**时才折叠，把三档击杀合成面板一直就支持的单一 Kills 行。**带子 ≥270px（含 286/400/588/800/1080）一律保持 30 行**，与旧行为完全一致；过短的带子（≤200px，两行买不到任何字号）同样保持 30 行。实测只有 220px 与 252–269px 这类「刚好差一像素」的区间才折叠。
- **C：`UsesBandBelowActions` 的比较口径**。该策略问的是「这条带子装不下板、而页面动作下方那条带装得下」，过去传入的是可读下限 270px，于是下方那条 85–88px 的自由带永远不可能通过——这条逃生路径在 1440 高的页面上一次都没进过。现在传入房间解算出的可画高度。**如实说明**：本次日志那页的下方带只有 85–88px，对 135px 的可画网格仍然不够，所以该页**依然不会**走这条分支；修的是「问题能不能被回答」，不是「这条分支现在会走」。
- **验证**：`PASS: 2705 combat-panel assertions`（1.19.19 为 2669，+36：A/D 的 269↔286 悬崖、无测量回退、100px 仍被拒；B 的 ≥270px 不裁行 / ≤200px 不裁行 / 269px 折叠 / NaN 保护；C 的四种 `UsesBandBelowActions` 情形）。`Scan` 38、`Supply` 50 均 PASS。`ConfigWatcher` 在本机仍为 6 个缺少 `BepInEx` 引用的编译错误，与本次改动无关（`git stash` 前后同为 6 个）。
- **未验证 / 未改动**：`ResultsDisplay.cs` 不在 smoke 套件的编译范围内（csproj 只链接 `LayoutPolicy.cs`、`ImpactBoard.cs`），所以 `Prepare` / `SuccessRegion` 的接线只经语法解析、**没有运行时测试覆盖**，需要在有游戏环境的机器上编一次并进 1920×1080 的结算页看日志是否出现 `glyph 6px` 而不再是 `need=270px ... deferred`。评分权重与公式、快照协议、网络同步、HUD、失败页的标题锚点与客机固定几何、`F8` 行为均未改动。

## 1.19.19
- **新增结算称号「全能中坚」（称号契约的一处变更）**：旧规则下，四平八稳、每一项都是队内第二的玩家会拿到综合评分 `#1` 却配一句「平平无奇」，观感自相矛盾。现在落空的人按名次收尾：**名次为 `#1` 且没有任何单项独占时授予「全能中坚」**，`#2` 及以后仍是「平平无奇」。判定只看两件事——`AssignRatings` 走完「自己独占了哪一项」之后仍无所得，以及界面显示用的同一个 `ImpactEntry.Rank` 是否为 1，所以并列第一名（两人同为 `#1` 且都没独占）两人都拿这一句；第一名本身若独占某项（例如「清道夫」），仍保留那一项的称号，不会被改判。新称号和「平平无奇」同属兜底语义，不写入 `used`，可以被重复授予。授予判据读的是结算看板打印的那个一位小数分（`IsDisplayedZero`，与 `#N` 同一行看到的数字），所以「显示 `0.0`」与「能拿第一名称号」在代码与文档里是同一件事：全队显示分都是 `0.0` 时没有「第一」可站，一律保持「平平无奇」。`CombatPanel-config/scoring.json` 的 `Titles` / `Reasons` 各多一个 `AllRound` 条目（`Reasons` 不带占位符），改文案与其它称号一样遵循「留出厂文本即跟随语言设置」。
- **结算看板「说明」行**：新称号下输出「综合评分全队第一，无单项领先」，不再借用「平平无奇」那条按伤害与击杀拼出来的句子；该句没有占位符，因此没有新增任何占位符机制。
- **README 与代码不符的表述改准**：①「四名玩家评价一定各不相同 / 什么都没领先的玩家也能拿到一句属于自己的」改为「有单项独占的人各拿一句，落空的人退回兜底称号，兜底不占位、可以重复」；②称号列表里的「阵亡 = 铁壁生存」改为代码实际的「仰卧起坐」；③「十三项指标按权重降序排列」改为「按指标枚举顺序输出，最重的单人存活 (1.60) 排第 9 行」，同一张表里的分隔行标签也从「—— 以下按权重降序 ——」改成实际的「指标」；④「显示分 `0.0` 固定拿战地游客」改为代码实际的「平平无奇」（`AssignRatings` 从不授予「战地游客」）。`Thunderstore/README.md` 里同一套表述同步改准，并补上「全能中坚」这一档；⑤`CONTEXT.md` 与 `COMPATIBILITY-REPORT.md` 里同一条「显示 `0.0` → 战地游客」的陈旧口径也改成「显示 `0.0` → 中性称号「平平无奇」；`ZeroScore` 只作为兼容键保留、不参与分配」。
- **中英混排修正**：「Scout 击杀 N 只」改为本模组自己的中文叫法「触手击杀 N 只」，与行标签「触手击杀 / 沉睡 / 伤害」、称号「触手猎手」一致；出厂 `Reasons.ScoutKills`、`Titles.ScoutKills.Description` 与 `scoring.json` 的 `Guidance` 同步改口。英文文案（`N Scouts killed`）保持不变，英文枚举与 JSON key 也不变。
- **友伤容差阈值 `FriendlyFireGrace`（一处评分输入处理，权重与公式未动）**：友伤是反向指标，归一值是 `1 − 值 / 全队最大`，于是「别人都是 0、自己有一点」就等于「全场唯一最差」——过去 10 点友伤和 3000 点友伤后果完全一样：必得「敌我不分」，同时丢掉该项权重 `0.75 / 9.68 ≈ 7.7%` 的分。现在 `scoring.json` 新增绝对阈值 `FriendlyFireGrace`（默认 **10**，范围 0–1000，单位与面板显示的敌伤相同）：**不超过它的友伤「伤害」在进入评分前按 0 计**，再走原有归一流程，所以「全队有效友伤伤害都是 0」时该项自然落到既有的「该项无人得分」分支，没有新增任何特判或魔法值；**超过阈值的伤害与过去完全一致**（仍按全队最大友伤归一、仍是「敌我不分」的候选）。权重 `0.75`、权重合计 9.68、评分公式、`Normalize`、`Clamp`、角色加成与分母累加方式均未改动。
- **容差只作用于「友伤伤害」，友伤致倒次数不受容差影响（有意为之的口径，不是遗漏）**：`FriendlyFireDeaths`（友伤致倒）照旧参与该项归一，仍可能让玩家拿到「敌我不分」，所以「不超过 10 点就整项豁免」是错误读法。由此有一个既定结果：**A 友伤 40 点、0 次友伤致倒；B 友伤 8 点（在容差内）、1 次友伤致倒 → 两人严重度都是 `0.5`**（A = 伤害满额 + 致倒 0，B = 伤害按 0 计 + 致倒满额，两个分量等权平均），严重度并列 → 该项没有唯一最差者 → **谁都不获「敌我不分」**。这是「只有唯一最差才授称号」的既有并列语义导致的既定结果，不是漏判；若要让致倒也吃容差，那是一次新的契约变更，本轮不做。
- **称号显示名调整：「反复倒地」改为「仰卧起坐」**：只改中文显示名（结算板的评价列、`scoring.json` 的 `Titles.Downs` 出厂标题、README 的称号列表），判定逻辑与授予条件未变；英文文案（`Frequent faller`）、枚举名与 JSON key（`Downs`）都没有动，既有用户配置继续生效。
- **验证（2026-11-05，pwsh 7）**：`scripts/Verify.ps1` 对本机 r2modman profile 的真实 BepInEx / Interop 程序集运行 → `VERIFY: PASS`，插件 Release 构建 **0 警告 / 0 错误**，`PASS: 2666 combat-panel assertions`（1.19.18 为 2638；同一版本内三批共 +28：新称号 7 条 + 友伤容差 19 条 + 「仰卧起坐」显示名 2 条，其中友伤容差覆盖「容差内唯一友伤不评奖且不亏分」「超过容差照旧评奖并保持满额惩罚」「全队在容差内仍有有限分」「容差内 + 友伤致倒仍评奖」「40 点 0 致倒与 8 点 1 致倒严重度并列 → 无人获称号」「grace=0 严格模式」「夹取 1000 与 NaN/负值回退」「抬高容差后同一笔友伤不再评奖」「配置解析、非法值拒绝与磁盘往返」「第一名判据取显示分」），配置监听 9 / 补给归属 50 / 扫描重放 38；`SCOUT_HOOK_SAFETY` / `OPTIONAL_EWC_BRIDGE` / `EWC_API_CONTRACT` 与全部 wiring 检查 PASS。
- **未改**：评分权重（含友伤 0.75）与合计 9.68、评分公式、`Normalize` / `Clamp` / 角色加成、名次与并列规则、`CountAtMax` 与金牌逻辑、快照协议 **v8**（字段/版本/语义）、`SyncProtocol` / `CombatMerge` 与网络同步路径、布局/列宽/行序/锚点/时序/可见性门控、`F8` 行为、其余配置默认值。本轮唯一被批准的评分输入改动就是「友伤伤害进入归一前按容差归零」这一处；新称号的授予判据从「原始分 > 0」收紧为「显示分不是 `0.0`」，评分、排名与并列规则本身未动。

## 1.19.18
- **根因（结算板上界太松、下界失效）：客机成功页把「整块完成区最深可见处」当成上界、把「屏幕底 − 8」当成下界，而 1.19.17 的兜底档位 ① 又是「按钮下方自由带/屏幕安全区」**。成功页的主机/客机两条分支里，上界都来自 `CompletionBounds.Deepest` 对「白板 `m_sectorsWhiteBox` + 分区标签 `m_sectorHeader` + 四个分区图标」取最深处——白板是一块画在图标下方的底板，于是上界被它拉到远低于图标行的位置；客机分支的下界则由 `ResultsGuestPageGeometry` 取 `screenHeight − 8·scale`，完全不看原生那两行字。实机截图（2560×1440 的客机成功页）：分区图标行底边约在 250/1080 处，我们的板顶却在 575/1080 处（上方空掉一整片），板底到 1030/1080，**直接从原生「正在等待……」与「送回大厅」两行字上压过去**。1.19.17 的兜底路径在客机上同样错：它的档位 ① 是「按钮下方自由带 / 屏幕安全区」，把等待文字吃进条带里正是它。
- **新规则（新增纯托管 `ResultsBounds.cs`）：一条带，两个边，两个角色共用，永不放宽**。**上界** = 「已清理分区」图标行（`m_sectorHeader` 标签 + `m_sectorIconMain/Second/Third/AllCompleted` 四个图标，**不含白板**）的实测底边 + 净空；本帧测不到用上一帧可信值（`_iconRowBottom`，随页面更换清空），两者都没有才退到 `0.10·屏高`。**下界** = 页面上真实可测的三个下墙取最高者再减同一净空：客机的等待状态文字块（`FooterTextTop`：在 `m_btnLeaveExpedition` 子树里用 `GetComponentsInChildren<TextMeshPro>(true)` 取最高顶边，并按世界空间文字用菜单相机投影，即 `TryScreenRect` 的那条规则；测不到则退回该控件自身的布局矩形）、主机的「送回大厅」按钮（pressable 或 laid-out 都算）、以及交互扫描量到的任何控件。净空是**设计像素**：1080p 16px，按 `screenHeight/1080` 等比缩放（1440→21.3px、2160→32px）。带高不足 `MinimumBand`(48px) 时上界上移以保住下界并标记 `clamped=true`——下界是承诺，宁可变小也不越界。
- **板自上界向下顶对齐，带高决定行高与字号（映射写进注释与断言）**：`ResultsBandFit` 把带高花在固定行数上——`rowBudget = bandHeight / rows`；`rowHeight = max(font × 1.45 × density.Row, font × 1.5em)`（这正是 `HudTable.BuildGrid` 实际建行用的式子）；`font = floor(rowBudget / max(1.45×density.Row, 1.5))`。compact 密度下 1.45×0.80 = 1.16，但行高由 1.5em 的行距兜住，所以：**588px 带 / 30 行 → 13px 字号**（与实机日志里 `glyph 12px`/`13px` 逐像素吻合）、**997px 带（本次客机）/ 30 行 → 22px**（再受宽度与可读性上限约束）、**200px 带 / 30 行 → 4px 字号、行高 6px，30×6=180 ≤ 200**（低于 6px 时记为 `squeezed`，行高与字形一起缩，条带不被越过）。`HudTable.BuildGrid` 的 `minimumPixels` 不再被强制抬到 6（默认值仍是 6，关卡内 HUD 行为不变），调用方给的下限被如实执行，带太矮时才有真正可用的退化。
- **严格路径与兜底路径接到同一条带上**：成功页 `SuccessRegion` 在两条角色分支之后统一用 `ResultsBounds.TryResolve` 覆盖/收紧条带（`top = 图标行底 + 净空`，`bottom = min(带下沿, 原条带下沿)`；1.19.16 的「按钮下方自由带」`BelowActions` 原样保留，因为那条带的两个边本身就是实测契约）；失败页 `FailureStrip` 用标题底边作上界、等待文字/按钮作下界收紧（只收紧、不放宽，玩家配置的纵向偏移与 1.19.13 的客机几何都保留）。**兜底路径先取这条带，只有在两个边都完全测不到时才退到屏幕安全区**，并且那时仍避开扫描量到的任何控件；顺序在断言里钉死（`FallbackPlacement` → `ResultsBounds.TryResolve` → 之后才是 `ResultFallbackLayout.TryResolve`）。

## 1.19.1
- **Squad sharing works again, which is what 1.19.0 broke.** 1.19.0 refused to send anything - a greeting included - to a player it had no proof about, and required either a named SteamID64 or a packet from the other side first. Two machines that both waited therefore shared nothing at all, which is exactly what both logs from that session say: `not one packet heard from any of them`, on the host and on the client. This build shares with every player in the slot list by default, over the transport the rest of the GTFO modding scene already broadcasts on (GTFO-API's free-sized network event), whose bytes carry their own key, magic and version signature and are dropped by a machine that runs no mod without a handler being asked for one. A client also sends its own row straight to the other clients, so two clients no longer depend on what a host could measure about them.
- `[Squad Sync] ShareWithEveryPlayer` (`true` by default) turns that off for a lobby that should stay restricted; `[Squad Sync] AllowlistedPeers` is then the way in, exactly as before. Both are re-read while the game runs, and a configuration file that cannot be read falls back to sharing rather than to silence.
- The transport is chosen per machine and confirmed per peer: GTFO-API's event when the library is loaded, the game's own byte channel when it is not, and until a peer has answered the packet goes out both ways so a squad that mixes the two still pairs up. Which route a peer actually used is remembered, so the duplicate costs one packet per peer rather than one per second.
- **Blood loss is measured from the health a player actually lost, not from the health one damage method happened to move.** A watermark per player is fed by every path that reports a figure - the damage entry points, the replicated health update a host sees a client's blows through, the revive, the spawn that sets them up - and only a decrease against an unchanged maximum is credited, once, however many paths report it. A maximum that moves in either direction is not blood loss, and a host now shows blood loss for a player it never applied a blow to. This is the "blood loss missing on the host" and the "blood loss wrong" report.
- The settlement board is sized by measurement instead of by a multiplier: the table is measured at a candidate glyph size and the size is bisected up until it fills 92-96% of the strip between the completion section and the return-to-lobby button, or until it reaches the page's width or 3.5x the in-level size. On a 2560x1440 success page that is a table of roughly 1960x880 spread to the full 2512px width, where 1.19.0 drew about 600x370 in the middle of the same room. Columns 2-5 still share one width, the widest of them.
- A squad packet queue that overflowed emptied itself and then stayed latched at the overflow count, which cost every later packet of the session; the bound now drops the oldest entry and nothing else.
- **The `说明` line under each `评价` is customisable too, in the same `scoring.json`.** `Reasons` carries one template per settlement sentence, with the figures available as placeholders (`{damage}`, `{share}`, `{count}`, `{kills}`, `{deaths}`, `{uses}`, `{firstMarks}`, `{weakspots}`, `{hits}`, `{shots}`, `{efficiency}`) - each key accepts only the placeholders that sentence actually has. A template left exactly as shipped keeps following the language setting, an unknown placeholder or an over-long line makes the file invalid and the previous valid configuration is kept, and an empty template prints no explanation for that row.
- Protocol is unchanged from 1.19.0 (8), so the figures are read the same way, but 1.19.0 still sends nothing: both machines have to be on 1.19.1 to exchange anything.

## 1.18.0
- Settlement titles are JSON-configurable, each with its own description: total damage, minor/elite/BOSS kills, melee and Scout kills. Giving a pack away is not a use by the giver, a full-health pack with no benefit is not counted, healing never offsets the loss, and a maximum-health change is not a loss.

A kill total and its split are one block and are taken from one machine, so a cell can never print a subset larger than its count.
